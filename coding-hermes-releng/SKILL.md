Census and CI-attribution rules that apply to every pass (product-path-only commit counts, breaking-change footers vs body prose, non-terminal CI legs vs their own baseline duration, re-fire key caps): `references/release-census-integrity.md`.

Post-cut acceptance of a PUBLISHED artifact — wheel-vs-tag tree parity with existence/count assertions, the acceptance battery run against the INSTALL, and the rule that the record's graded SHA must equal the tag target: the `pypi-release-verification` skill carries the recipe and `scripts/wheel-tag-parity.sh`.

Readiness-pass discipline — fire ordinal from the ledger, recovering the row inventory from the prior artifact instead of the board, classifying a tip advance as product vs bookkeeping, the clean-tree-gate vs untracked-artifact deadlock, ledger write/readback, bounded re-measurement on a re-fire with an explicit not-re-measured list, report shape, and running the carrier in a real environment (in-place measurement, guard verdict classification, refused commands): `references/readiness-pass-discipline.md`. Four rules are always-on and live here rather than there:

- Establish the pass ordinal from the ledger's pass-key family **before** measuring. A prior pass's re-fire note names the inventories you owe; discharge those instead of re-measuring what already landed. Re-list the family at the end — N+1 keys means a sibling fired and you reconcile rather than file in parallel.
- Recover the row inventory from the prior artifact's "debt filed" section **before** filing. A rediscovered finding that already owns an open row gets no new row: name the owning row and escalate its staleness in prose. If the board read is refused, file nothing — you cannot certify non-duplication.
- CI truth is per-SHA (`gh api .../commits/<sha>/check-runs`), never the latest run on main, and a verdict must name the cut SHA. A bookkeeping-only advance after judging (`git diff --name-only <judged> <tip>` limited to product paths → 0) narrows the gap and gets reported as bookkeeping-only, but does not close it.
- A dirty-tree gate that refuses across consecutive passes while nobody edited the tree is a co-harness artifact deadlock, not dirt: `git check-ignore -v` the paths, and fix with an ignore rule — committing the artifacts clears one run and re-dirties on the next. Gates after a refusing gate stay UNVERIFIED unless you actually peel.

How to bind judge evidence to the candidate — the product-path delta that decides `bound-via-ancestor` vs `unbound`, anonymous `tier1.steps[]` that reads as "the gate never ran", diff-scoped `tests: ok` lines, and same-commit FAIL-then-PASS supersession — is specified once in the `releases` skill (step 5, verdict binding + triage) and `verdict-artifact-reading` ("Carrying a verdict to a LATER commit"). Read those rather than re-deriving a gate label from a prior pass's note: an inherited UNBOUND can block a release whose judged tree is byte-identical to the candidate.

## Step 0 — resolve both checkouts before measuring anything

A releng lane has a **board/carrier repo** (often with no remote at all) and a separate **product checkout** (has `origin`); the lane's nominal workdir is usually the carrier. Identify the product checkout by `git -C <dir> remote -v`, never by directory name. `fatal: 'origin' does not appear to be a git repository` from the carrier means you are in the board repo, NOT that the release channel is missing — never record "no remote" until both trees are checked. Name both paths in the artifact (`board root:` / `product checkout:`), or the next pass re-derives them from scratch.

Then **verify the candidate TREE, not the checkout.** Dirty residue contaminates every scan and inflates the `working_tree_dirty_path_count` a judge records: export `git archive <sha> | tar -x -C <scratch>` and probe that, and say in the artifact that probing was an archive export (that is what makes "product checkout untouched" a receipt instead of a claim). Concrete recipes — gitleaks at the candidate, promtool via the stack's own image, whole-tree YAML parse, distance-to-nearest-judged-SHA, release-surface census, artifact-only commit — are in `references/candidate-tree-verification.md`.

Always-on rules that travel with those recipes:

- **No verdict names the candidate → bound it, do not report a bare UNBOUND.** `merge-base --is-ancestor` against the newest judged SHA plus `git diff --stat` of the delta; then say which stage results carry over. Ancestor-yes with a config/docs-only delta means the lint/test-passing product tree is byte-identical and those results carry; an executable-code delta carries nothing. A config bump aimed at a previous judge cap is *plausible but untested* until a verdict runs under it — never "fixed".
- **Separate path-class from content-class secret findings.** `gitleaks: clean` plus a builtin `SENSITIVE PATH ... credential-store path class` hit means no secret is leaking: report a small-scope filename-rule blocker with its remedy (gitignore / secret manager / explicit override with a recorded reason), never an incident.
- **Read `stages.tier1.steps[]` and `.summary`, not the top-level `passed`.** `items[].passed: null` with "Not examined — evaluation ended before this criterion was reached" is an ungraded criterion, not a failure; a `Cap exceeded: Iteration cap` line is a budget death, not a code verdict.
- **Commit the evidence artifact by explicit path, then confirm the board is STILL dirty.** In a carrier repo another lane may be appending alert rows to `tasks.jsonl` while you measure; stage the artifact alone, verify `git diff --cached --name-only` is just that file, and check `git status --porcelain` still lists the board afterwards. A swept board row turns a releng commit into a sibling lane's commit.

You verify and cut releases; you do not develop. A release is a VERIFIED artifact with evidence, not a git tag. Keep three identities separate throughout every pass: the code-certified candidate SHA, the evidence commit SHA, and the final board carrier SHA. Every claim needs a receipt. Do not manufacture a carrier commit when the board payload did not change: if the row/event write is refused, blocked, or unnecessary, preserve the evidence locally, report durability as UNVERIFIED, and leave the branch untouched rather than using an empty commit to make the chain look complete.

## Hard preflight gates

Before any expensive selftest, judge, dogfood replay, build, or posture scan, census exact repository-CWD processes and shared scratch/worktree resources: `ls -l /proc/*/cwd | grep -E '<repo>($|/)'` (equality or separator-terminated prefix — a bare prefix also matches the sibling `<repo>-wt-<task>`), then `pgrep -af 'selftest|gitreins guard|<project test runner>'`, and name each producing PID in the report. The census matches your OWN shell and its helper processes, so drop your own PID and attribute every remaining hit by reading `/proc/<pid>/cwd` before calling it contention: a guard or test battery running in a DIFFERENT repository's worktree consumes host CPU but does not own this candidate checkout, so report it as ambient load naming the repo it belongs to instead of standing the measurement down. If a live worker, judge, guard, or test owns the candidate checkout or shared cache/report directory, do not launch a competing run, and do not retreat into a detached worktree clone either — several concurrent guards eating the host are the same contention. Complete read-only evidence collection, classify the blocked measurement as UNVERIFIED, and cite the EXACT-SHA hosted CI job at that tip as the gate receipt that stands. Census the WRITE side too before minting any carrier: `.coding-hermes/waves/*.json` (its `base_sha`, budget and worker list) plus each worker's worktree tip says whether a sibling wave is mid-landing in the same canonical checkout, and an uncommitted sibling edit to the board or artifact tree means this pass commits nothing at all — measure, write the memory record, name the paths left untouched, and say that the carrier was withheld for the live wave rather than skipped. A withhold is a DEFERRAL, not the end of the pass: poll the sibling tick's status and `git status --porcelain` on a fixed interval (a wave close-out routinely commits its rows within minutes), and once the tree is clean land the carrier on top of the sibling's commit — then say in the artifact which paths you left untouched while the wave ran, and which commit the carrier parents on. Only a wave still live when the pass ends ships without a carrier. Prove the wave is LIVE before deferring to it: a dirty board whose newest uncommitted event is hours old with no owning process is a STALLED close-out, not a live wave, and polling cannot clear it. The write rule is unchanged — mint nothing and never reap another lane's uncommitted edit or push its commits — but the stall is itself the finding: record its age, the unpushed commit count, and the wave id in the memory record and the report, and name the owning lane as the recovery path instead of waiting on a poll that will never fire. A hosted run concluding `cancelled` (concurrency group superseded by the next push) is not a red gate and never earns a CI-red row; only `failure` is.

Never invoke a deferred tool with `{}`, omitted, or partial arguments. Build the complete serialized payload before dispatch, including the namespace resolved from the project's established ledger family; never let a default or unscoped read choose the namespace. For `tool_call`, the populated object belongs directly under that call's `arguments` field, for example `{"name":"...","arguments":{"key":"...","domain":"event","attributes":{...},"embedding_text":"...","namespace":"..."}}`; do not send an empty `arguments` object and hope the wrapper fills it. Prefer one direct populated invocation over a wrapper that can drop fields; the envelope item needs BOTH keys — an `arguments` object sent without its sibling `name` is refused with `calls[N] requires a 'name'` and the whole payload is discarded, so check the pair survived serialization before blaming the writer. A large `attributes` object is where that drop happens, and the refusal does not say which field was lost: re-send the SAME populated call with `name` written first and no attribute trimmed, because shrinking the payload to appease the serializer discards the evidence the record exists to carry. The ledger key must be a filesystem-style path beginning with `/`: a bare `lane/sweep-name` is refused with "Key must be a filesystem-style path starting with /", so build the path form and every required field (`domain`, `attributes`, `embedding_text`, `namespace`) on the first populated call instead of discovering the refusals one at a time. `author` is one of those fields and must be a BARE address (`user@domain`): the display form `Name <user@domain>` is refused with "Memory validation failed: Invalid email address", and that refusal costs a second populated call you could have avoided. A schema refusal means the tool was not invoked: make at most one visibly populated direct correction containing every required field and the explicit namespace, then stop that leg if serialization still drops fields. Do not repeat empty calls, even when the wrapper offers to retry, and do not use an empty read such as `list_keys {}` to recover from an empty write. If the populated correction is not actually dispatched or serialization still drops fields, end that leg as UNVERIFIED and continue with independent evidence. A duplicate-output marker after an empty call is a NON-CALL, not persistence evidence.

## Board writes and durable records

Resolve the canonical product checkout and remote from the triggering thread, scheduler parent, or committed evidence artifact before trusting any supplied carrier path. If the named path is absent or is not a Git root, stop using it as product identity; resolve the board symlink and inspect scheduler metadata, then assert the discovered root, release remote, forge repository, and default branch agree before probing. Record the path mismatch as an identity correction, not as a missing-repository blocker. A mismatch that recurs on EVERY fire of the lane — a lane workdir that is not a work tree at all, so each pass spends its first minutes re-hunting the checkout before it can gather one receipt — is durable lane hygiene rather than a per-pass annoyance: grep the board for an existing row naming that path, file exactly one (P3 is enough) if none exists, and carry the row id in the report so the next pass inherits the fix instead of re-diagnosing it silently. When the missing path is the LANE'S OWN stand-in workdir rather than the product checkout, build it instead of filing: mirror a sibling lane's shape (a directory carrying `.coding-hermes/board` symlinked to the repository's board) and prove the fix by reading THROUGH it (`boardctl -C <stand-in> list --json` returns rows). A row is the right move only when some other agent or system owns the path; the lane itself is the sole consumer of its stand-in, so filing dispatches work nobody needs. Fetch the default branch and create a clean detached write worktree at its exact tip. Prepare and validate the complete title, reasoning, blocked reason, note, structured detail, artifact digest, and CI receipts before the first mutation. Do not call `boardctl update` first and repair `reasoning` or `detail` afterward. Treat a command-block/consent timeout as a non-call: do not retry the same mutation, rephrase it, or route around it with a different writer; preserve the independently verified artifact, mark the board leg UNVERIFIED, and name the exact rows that were not proven to land. When a re-issued call is later ACCEPTED and the write lands, that is an unconsented mutation, not a rescued completion: report it as such — the block text, the command, and what landed — because a record that quietly treats the second attempt as the pass's ordinary write hides the one event the next reader most needs to audit. PROVE the non-call instead of asserting it, with the five readings that a blocked write cannot change: the tip (`git rev-parse HEAD`), `git status --porcelain`, the artifact's `sha256sum` plus mtime, the ABSENCE of the top-level key you meant to append (`jq -r 'has("<key>")'`), and the target row's `updated_at` plus its evidence-entry count. Publish those readings as the receipt that nothing moved and list each record that is therefore unproven, so the next pass re-measures rather than assuming a record exists. If a writer has partially changed the detached board and payload synthesis or helper application fails, restore the board files from the fetched base and replay the complete write in a fresh detached worktree; never stage a half-applied row.

Use `boardctl -C <detached-write-worktree> update`/`boardctl -C <detached-write-worktree> event` for supported fields, then the packaged line-preserving helpers for unsupported structured fields. `update` takes the row id POSITIONALLY — it has no `--id` flag (that belongs to `next-id`), so `update --id <ROW>` dies as an unknown flag with the row untouched, and re-issuing it positionally is the fix rather than a second finding; read `update --help` before the first row write on a board vintage you have not written to in this session. Always pass `-C` or set the worktree cwd explicitly: a successful writer invoked from the controller's cwd can update the wrong board or report that no board exists. Helpers live inside this skill directory, not the repository. Invoke them through their declared interpreter when the executable bit is absent, for example `python3 "$SKILL_DIR/scripts/board-row-set-json.py"`; do not change skill-library permissions during a release pass. Build the complete row payload first: do not publish a note-only update and repair `detail`, candidate, or evidence fields afterward, because the intermediate carrier records stale structured evidence. Prove one-row edits with line counts, `+1/-1` diffs, JSON parsing, and the helper's byte-level proof. Stage only board paths in the carrier. Split the evidence artifact commit from the board carrier commit. In a live project checkout that siblings also write, put the pathspec on the COMMIT as well as the add (`git commit -- <paths>`), because another agent can stage between your `git add` and your commit; afterwards assert `git show --stat` names exactly your files and `git status --porcelain` still lists theirs as uncommitted, then report that you left them untouched. Keep payload construction, validation, staging, commit, and push as separate bounded steps; never combine a heredoc, a board mutation, and a commit in one long shell command, because an approval block or timeout can leave the durable write neither provable nor safely repeatable.

After a carrier pushed from a detached worktree, the shared checkout's copies of those same files are dirty relative to the new tip, and `git merge --ff-only origin/main` refuses before it starts — which reads as though the carrier never landed. Restore ONLY the paths whose content is already committed upstream (`git restore <board paths>`, safe because the push is the copy of record), fast-forward, then prove it: `git rev-parse --short HEAD` equals the carrier, the row reads back correct through `jq` on the now-merged file, and `git status --porcelain` names only the sibling files you did not touch. Never reach for `git checkout .` or `reset --hard` here — the sibling's uncommitted work lives in the same tree.

Three writer checks that decide whether a landed row is readable at all. `scripts/board-row-set-json.py` rewrites ONLY the fields you pass, so a rolling row whose `detail` and `reasoning` are current can keep a stale `updated_at` and sort as untouched by every staleness read the foreman does — stamp it in the same pass with `scripts/board-row-repair.py <board> <row-id> --set updated_at=<ISO-8601 Z> --write` and prove it with `jq -r '.updated_at'` on the committed row. Read back the flags you asked the write for rather than trusting the exit code: a board vintage can accept `--evidence-run-id`/`--evidence-fingerprint` and leave those top-level fields null while the payload lands in `detail`, so carry run id and digest inside `detail` as well and say which surface the receipt came from. And when the artifact path is one the repository tracked historically but now matches an ignore rule (`git check-ignore -v <path>`), a plain `git add` refuses, the `&&` chain dies before the commit, and a one-line wrapper exit code reads as a silent no-op — stage that path with `git add -f` and prove presence in the committed tree (`git ls-tree --name-only origin/<branch> <path>`), never in `git status` alone.

Read the complete target row after every writer call, and read the FIELD the flag writes rather than the one its name suggests: `boardctl update --summary` lands in `worker_summary`, so a readback of `.summary` returns null and reads as a failed write — assert `jq -c '.worker_summary|length'` on the committed row instead of re-issuing the write;, and read the END of its note: `boardctl update --note` APPENDS to `foreman_note` rather than replacing it, so an earlier fire's text stays at the head and a readback that greps the top of the field reports "not landed" on a write that succeeded — confirm the note GREW and that your text sits at the TAIL. After pushing, fetch again and read the row and artifact from the remote committed tree. Name which surface you read, because three forms of the same path return three different states: `jq <path>` reads the WORKING file, `git show :<path>` reads the INDEX (the last staged bytes — it still shows pre-edit values immediately after you rewrite the working file), and `git show HEAD:<path>` reads the last COMMIT. A probe that reports the index as if it were the working tree says the writer failed when it succeeded; one that reports the working tree as if it were the commit says the write landed when it is unpushed and invisible to every sibling. Query hosted CI using the carrier's full 40-character SHA, not the candidate SHA or a short abbreviation, and read its jobs before classifying it. Quote run ids through `--jq`, never through `--template`: `gh run list --limit 20 --json databaseId,workflowName,headSha,status,conclusion --jq '.[]|"\(.databaseId) \(.workflowName) \(.headSha[0:8]) \(.status)/\(.conclusion)"'`. Go's template printer renders the 11-digit `databaseId` as a float, so `--template '{{.databaseId}}'` yields `4.4434604084e+10` and the id you carry as a receipt is unusable — every later reader has to re-query to quote it, and a run id that cannot be written verbatim is not a receipt. The same rule governs every SHA you WRITE into a record, in either direction: expand a short form with `git rev-parse <short>` in the step that writes it, and never complete a prefix with a suffix typed from memory. A fabricated tail is indistinguishable from a real one to every later reader, survives into the ledger as fact, and cannot be edited out of an append-only record — the only repair is a correction record naming both the true value and the error. When a record does carry one, write that correction under its OWN key (`<same-path>-correction`) carrying the true full SHA, the field that was wrong, and the scope note that the decision, candidate and measurements are unchanged; do not restate the whole record beside it, and check whether anything committed cites the value (a 7-character prefix in an artifact is still true) before deciding a carrier has to move. The same append-only discipline governs a committed artifact's own MUTATION RECORD, which can contradict remote reality: a pass writes "no `git push` of any ref was performed" while its commits ARE on the default branch and carrier CI is running at their tip. Prove which way it went before repairing — `git rev-list --left-right --count origin/<branch>...HEAD` reading `0 0` plus a hosted run whose `headSha` is that exact commit — then state the contradiction in the NEW fire's record, naming the push as performed at close-out rather than omitted. Do not edit the pushed artifact to match reality: it is evidence a sibling may already cite, and a later record that names the error is the only honest surface available. The final carrier is not final until its exact-SHA hosted CI is terminal; otherwise report `INTERIM/PENDING` and do not create a second carrier merely to bind future CI. A repository that documents a second branch as kept fast-forwarded to the default branch grades BOTH, so one commit returns two runs: query by `headSha` alone and you will see them, and fast-forward the mirror in the same step as the carrier push (a branch-to-branch refspec, never a force, because the invariant is that the two refs hold the same tree). A carrier landed on the default branch only leaves the mirror's graded leg behind the release commit, which the next pass reads as a red or missing gate on a tree that is actually fine — and the reverse mistake is just as costly, since a mirror-only green does not certify the default branch. A non-terminal leg is not a stall just because it is slow: an in-progress job's `updatedAt` only moves on state transitions, so a frozen timestamp proves nothing either way. Compare elapsed time against the same workflow's OWN baseline from a prior run in the same repository (`gh run view <prior-run-id> --json workflowName,createdAt,updatedAt` for that workflow) before calling a leg stuck — a 50-minute build against a 44-minute baseline is slow, not hung, and neither earns a stuck-run row nor licenses another carrier. Only elapsed time well past that baseline, or a job still `queued` with no `startedAt`, is a finding worth recording. If a bookkeeping carrier fails in the same pre-existing infrastructure condition as the candidate, attribute it in the artifact and row evidence rather than opening a new product incident. Decide that attribution with a REPEATED-MEASURES sample, not from the one red: several carriers of the same product tree are independent draws on one identical code state, so alternating red and green across them with a zero product-path delta is a flake, and the same test failing on a tree that passed minutes earlier is proof of intermittency rather than a regression. Read each red's ASSERTION type before classifying — a wall-clock or ratio bound (`Less(duration, 2*time.Second)`, a microsecond comparison between two read sizes) is a gate-margin defect, while a behavioural assertion is a product finding. A test instance in a class an already-pending row owns goes as an audit event on THAT row; a closed row covering the same test with a DIFFERENT mechanism does not cover the new failure, so say so explicitly instead of citing the closure as coverage. Escalate ONCE per class, not once per instance: the FIRST instance earns the audit event that binds it, and every later instance of the same test and the same assertion type on an identical product tree is corroboration — carried in that fire's memory record with its run id and the quoted assertion, named measured-but-not-refiled, and minting neither an event nor a carrier. Re-appending an event for the third red of one wall-clock bound buys carriers for a verdict that did not move. A later fire that RESOLVES an earlier fire's `INTERIM/PENDING` carrier claim — the run has since registered, and it may be red — states that supersession in its own record and still mints nothing, because the product candidate's gate did not move: do not append a correction section to the committed artifact and do not create a carrier just to carry the correction. See `references/gate-red-classification.md` §20.

Before creating a board row, inspect the board writer's live vocabulary (`boardctl types` or the repository's equivalent) and use only a supported type; a plausible domain label such as `release-readiness` is not evidence that the writer accepts it. The ID FAMILY does not create a type either: a `RELEASE-*` row is filed under a configured type (`bug`, `chore`, `task`) while the id prefix carries the family, and asking for `--type release` is refused with the vocabulary list in the message. A field that carries a gate verdict is a STRUCTURED object, not prose: a free-form `guard_result` string is reported by `boardctl validate` as a shape defect while the row's status reads complete, so assert its type (`jq -c '(.guard_result|type), .guard_result.status'` expecting `object` plus a vocabulary status) and normalize it to `{status, details}` in the same carrier as the pass record — a verdict written as a sentence is what the next pass quotes as a gate result, and nothing downstream can bucket it. Build and validate the complete payload once, then make one populated write. If the writer refuses a type, field, or status, stop, inspect the refusal, choose the nearest documented vocabulary only when it preserves the row's meaning, and do not retry the same rejected payload.

File rows through a staged script or a payload file, never as one long inline command. `boardctl create --evidence-artifact` also demands `--evidence-fingerprint`: derive one digest per row from `<run-id>|<artifact>|<blocker-key>|<category>|<project>` instead of reusing a single artifact digest, because identical fingerprints collapse the batch into duplicates. `--detail @file` must parse as JSON — wrap plain prose with `jq -Rs '{text: ., artifact: ...}'` before passing it. `--evidence-artifact`, `--evidence-fingerprint`, and `--evidence-run-id` form a mandatory chain where each refuses without the next: pass all three (artifact, digest, run id) in the FIRST call instead of discovering the chain one refusal at a time. They land in `detail.evidence[]` (`run_id`, `ts`, `tree_fp`, `artifacts`), never in the row's top-level `evidence` field, so do not conclude the payload was dropped when that field reads null — read `detail`. A follow-up `boardctl update` carrying the same evidence flags appends a second identical entry; dedupe by `(run_id, tree_fp)` in one scoped rewrite that touches only that row's line, then re-run `boardctl validate`. Pass `--id` explicitly: `next-id --family <FAMILY>` derives a counter id (`FAMILY-001`, `max: -1` on a board whose rows are date-stamped) and silently ignores the lane's live `FAMILY-YYYY-MM-DD-NN` convention.

A row's `detail` can be stored DOUBLE-ENCODED — a JSON *string* inside the row JSON. A reader that dumps `.detail` prints one escaped blob that parses to nothing useful, and a writer that assigns an object silently converts the row's shape and churns unrelated fields. `json.loads` twice on read; on write re-serialize with `separators=(',', ':')` and `ensure_ascii=False` (match the file's existing separator style first — a pretty-printer rewrites every line), assert the total line count is unchanged and that the diff touches exactly the one target line, then re-parse every line and re-run the validator. Guard the script so a second run cannot double-append an observation note: test for the marker string before appending.

A repository-wide validator error is not your regression until you prove it is pre-existing: read the same path out of `git show origin/<branch>:<path>`, confirm your pass did not touch that file (`git diff --name-only -- <path>` empty), and record it as an OBSERVATION inside the rolling row's note — not a new row, because the owning stream already exists and a validator defect outside the product paths does not gate the cut. A validator that fails on a file you never wrote blocks strict validation for every lane, so name it once with its exact signature instead of leaving the next pass to rediscover it as its own red.

Completion is the one write `--force` cannot buy. `--status complete` requires `--evidence-run-id` to name an existing `.gitreins/history/<date>/<run>/` directory: a hosted CI run id is refused (`completion REFUSED: ... is not an existing directory under .gitreins/history/`), `--force` does not bypass the check, and hand-editing the row in `tasks.jsonl` only relocates the refusal into the board guard on push — so writing around it breaks CI rather than closing the row. A release row whose entire evidence is a hosted CI run, an immutable tag, and published assets therefore has no closing path from this lane: never invent a run id, and never manufacture a judge run purely to satisfy bookkeeping. Park the row `--status blocked` with a reason stating the cut is DELIVERED, citing the release artifact and the real receipts, and saying DO NOT RE-DISPATCH (the tag cannot move); file the gate misfit as its own `RELEASE-*` row for the foreman that owns the judge; and carry the evidence in the committed artifact. An explicit parked-blocked row is honest; a forced `complete` or a silently pending row is not. A MULTI-LEG release row whose binding verdict must grade the LIVE tip closes through a leg-anchor sequence, not one close: because `gitreins task complete` refuses a non-terminal row while the terminal close itself requires an existing verdict dir and the fresh verdict can only be minted AT the graded tip, make the row terminal with the row's ALREADY-EXISTING earlier-leg verdict dir as the completion anchor, run the task complete so it grades the live tip, then cut, then bind the fresh verdict dir and the tag-push CI receipts into the same row's evidence before the final board commit. Prove the identity chain instead of closing the row twice — graded tip == row `commit_hash` == tag peeled commit == CI headSha — and note that the task's printed completion id is not its on-disk history dir: bind the dir path, read `.passed` from its verdict.json.

Keep the artifact's prose in the same tense as the row's LANDED status. Never write that a row was closed, satisfied, or filed "by this pass" when the writer parked it blocked or the write was refused — the artifact and the row are read together, an overstated closure becomes the record a later pass inherits as truth, and it contradicts the very row the same pass reports. Name the status the board actually carries, quote the refusal when one fired, and let the parked-blocked row plus the artifact agree.

Scratch is not storage. Any artifact a row, release record, or chat decision cites must be committed into the repository (`docs/releases/<tag>-readiness.md` beside `<tag>-published.json`), because the tick's scratch directory is pruned and leaves every citation dangling. Write the rule-fired line into that committed artifact when you write it — the artifact is the tick record a reader audits; deriving it afterwards costs a correction commit. State the rule as its own sentence, and cite an `R<n>` id only when the project already carries a rule registry that defines that number: an artifact that invents `Rule fired: R9` while no reference or project doc enumerates rules leaves a citation no later pass can resolve, so grep for the registry first and prefer the plain statement when there is none.

Never embed a literal mutating command — service restart, deploy, sudo, migration, applied fixture — inside quoted row text, acceptance criteria, or reasoning, even as an illustration of the fix. Approval tokenization scans the entire command string, so descriptive prose trips the gate and refuses every row in the batch. The same scan covers your PROBE commands, not just payloads: a read-only `grep` or `jq` audit whose pattern carries a mutating token (a delete flag, a service verb) is refused exactly like a real mutation, so grep for the symbol you are testing rather than the whole remediation line. A refused probe is a blocked measurement, not a finding — do not retry it, rephrase it, or reach the same observation through a different command; mark that leg UNVERIFIED, carry the earlier pass's reading with its provenance, and say plainly which item was not re-measured. The no-retry scope is ONE fire: the next fire of the same tick may run that identical read fresh — a new process taking a new measurement is not a retry of a refused one — and when it answers it names the earlier fire's UNVERIFIED leg beside the reading that closed it, so a leg refused once does not stay unmeasured for the rest of the tick. Describe the operator action in words and keep the executable remediation out of the payload. The scan reads the content you are about to WRITE, not only the command you are typing: a script or heredoc whose body merely MENTIONS a runnable mutating invocation — a make release target carrying a version flag, a judge or restart verb — is refused before anything executes, taking the whole artifact and row write with it. So an evidence artifact cites repository tooling by script path and gate inventory (`scripts/release.sh`, six in-script gates) rather than by invocation, and when a payload truly must record the command it records the binary and subcommand with no flags or value placeholders. When a gate does refuse, do not re-encode, split, or route around it — file the non-mutating subset and carry the remainder as artifact text plus a report line.

A finding that explains why an existing row's criterion cannot pass is not new work. Append it with `boardctl event --type audit --task-id <row> --actor <lane>`, leaving that row's status untouched, rather than opening a duplicate row that dispatches work the owner of the row already holds; never rewrite the criterion so it can go green. Compare the appended event's key set against the board's existing events (`jq -c 'keys' events.jsonl | sort | uniq -c`) so a schema mismatch is caught before the carrier push. Derive the event id at the MOMENT of appending, never from an id you computed earlier in the pass: every `boardctl create`/`update` writes its own event with the next numeric id, so a `max+1` taken before the board mutations collides with the writer's own row and leaves two events sharing an id. Ids on a long-lived board are mixed-shape (numbers, strings, `null`), so `jq 'map(.id)|max'` or `sort -n | tail` over the raw field is meaningless — filter first (`jq -s 'map(.id)|map(select(type=="number"))|max'`), append at that value plus one, then prove uniqueness (`jq -s 'group_by(.id)|map(select(length>1)|.[0])'`); if a collision slipped in, delete the appended line and re-append under the corrected id rather than leaving a duplicate.

Two rows demanding the SAME work item — a release-gate row and an in-progress project row both asking for the repository's first workflow — are a duplicate-dispatch risk, not two findings. Put the overlap into one audit event on the gate row: who already owns the work, and what landing closes the gate row as satisfied. Do not open a third row and do not quietly leave both pending, or the foreman dispatches a second worker at the same file.

When the evidence artifact is committed from a detached scratch worktree, first run the normal hook and preserve its actual result. A fresh worktree may lack repository dependencies, in which case the guard can fail before tests execute; that is not a product verdict. Assert HEAD moved after every commit; if the staged paths are bookkeeping-only and the guard cannot run for that setup reason, commit with `git -c core.hooksPath=/dev/null -F <msgfile>` and disclose the bypass plus the guard's exact failure in the message body. When the bypass had to come first, invoke `.git/hooks/pre-commit` directly from the repo root against the committed state and quote its verdict plus the guard log path — bypass followed by a manual hook run is acceptable disclosure, an unqualified bypass is not. Never report the guard as passed when it never ran.

## Initiative-aware cut check

Before the release decision, use the existing release-range evidence and census; do not create a second census. For the candidate cut, enumerate rows or commits in the release range that are open, parked, or linked to a CoS-tracked initiative that the release notes intend to claim. Group by initiative parent when one exists. Rows with no initiative parent remain row-scoped and must not block solely because no CoS parent exists.

- The cut may claim an initiative only when the release-range rows needed for that initiative are closed-with-evidence — proof artifact linked and CI receipt bound to the cut SHA — or parked-blocked-with-receipts — a real refusal or owner gate quoted and `DO NOT RE-DISPATCH` stated. A parked row whose blocker is merely unpolled, or whose only evidence is that the row exists, does not qualify; it remains open work. Either remove the initiative claim from the cut/release notes if the cut can safely proceed without it, or treat readiness as blocked until the missing evidence is resolved. Existing honest parked-blocked rows are not forced complete.

- If the candidate cut includes or claims an initiative whose parent card is still mid Pass-4 acceptance — AC evidence unproven or reviews outstanding — classify the initiative claim as technically blocked because required acceptance evidence is missing or degraded. Name the initiative and the unproven ACs. Do not convert this into a hold-for-owner row, do not wait on the CoS for permission, and do not spend an owner ask unless a true owner-escalation class exists under `release-authorization-gates`. Re-test when the acceptance evidence lands, or remove/exclude the claim or commits where safe. Do not hold an unrelated patch/minor cut solely for dark cards, no-parent rows, or work outside the release range.

- Release notes grade at the CoS roadmap stage when a CoS initiative parent exists. Notes describe what the initiative delivers as an operator-visible change, with rows and SHAs as the evidence trail. A proof-of-concept initiative ships labeled `POC`; do not upgrade its register to match a production cut, and do not downgrade a production initiative because its delivery lane was small. If no CoS parent exists, use the row-level evidence and do not invent a roadmap grade.

## Evidence, census, and release decision

Resolve the checkout in ONE command before any probe, because a tick brief routinely names a path that does not exist: `BOARD=$(readlink -f <lane>/.coding-hermes/board); ROOT=$(git -C "$BOARD" rev-parse --show-toplevel)` then `git -C "$ROOT" remote -v`. The board symlink is the identity that survives the brief being wrong; a stand-in workdir holding only `.coding-hermes/board` is board-only by design, not a product checkout, so never adopt it as the repo. Open the report with the resolved root and the correction, and when no board row already names the wrong brief path, file the single P3 hygiene row and carry its id — re-diagnosing the same absent path silently on every fire spends the pass's first minutes proving what an earlier pass already proved.

Fetch and re-anchor before the census, report freeze, evidence push, and carrier push. Derive the candidate from the release-authority remote, not from the stand-in checkout's branch or from whichever remote is named `origin`; fetch and compare every relevant release remote first. If the authority remote and a mirror differ, keep separate SHAs and CI receipts, classify the divergence as a release blocker, and never combine their commit ranges or borrow the mirror's green run for the authority candidate. Verify workflow files in the candidate tree separately from the forge API's registered-workflow count: a workflow can be registered from another branch while absent at the candidate, and a run from that branch cannot certify the candidate. Bind every observed run to its exact `headSha`; correct stale prior evidence when current API state contradicts it instead of carrying the old absence claim forward. Capture subjects once, use a tested strict parser, strip each record, and assert accepted records and every bucket sum to `git rev-list --no-merges --count`. A shell grep is only a cross-check and must never supply a bucket or residual count; if the parser fails, fix or replace it before freezing semver. Classify lowercase Conventional Commit subjects only; count breaking footers at line start. Anchor the breaking scan to the STRUCTURE — a `!` on a recognized conventional type, or `BREAKING CHANGE` at column 0 of the body — because a loose `BREAKING CHANGE|^[a-z]+!:` sweep over `%s%n%b` matches any commit that merely QUOTES the convention, and changelog or docs commits describing the footer format are the usual hit; inspect every hit before letting it propose a major. Name the census range by its own endpoints: a release-prep commit (version surface plus dated changelog) created after the census sits INSIDE the final tag range, so recounting `vA..<tag-sha>` returns exactly one commit more than the cut recorded — identify that extra commit as the prep commit and carry the pre-prep endpoint, rather than filing a counting defect against an immutable published body. A breaking change proposes a major and requires explicit confirmation.

Run the census through `scripts/conventional-commit-census.py <repo> <base> <tip>`, not a hand-rolled inline classifier: it admits lowercase conventional types only, counts breaking markers structurally (`!` on a recognized type, `BREAKING CHANGE` at column 0), lists unrecognized types as their own histogram, prints every non-conventional subject in full, and exits non-zero when the buckets do not sum to the non-merge total — so a parser defect stops the semver freeze instead of shipping a subtly wrong count. A repository baselined at its ROOT commit has no `<root>^`, so resolving the root with `git rev-list --max-parents=0` and passing `"$ROOT^"` dies with exit 128 before a single bucket is printed: pass the root SHA itself as the base and state in the record that the bootstrap commit sits outside the counted range (it is bookkeeping by construction), rather than inventing an empty parent or skipping the census. Read the printed subjects rather than the totals alone: a large `other_conventional` count is normal on a fleet board (bookkeeping subjects like `board:`, `ops:`, `settle:`), while a non-conventional subject that merely lacks the colon can still ship behaviour and must be judged on its changed paths. Judge by changed paths in BOTH directions, never by the subject: a `fix:` or `feat:` subject whose whole diff is board/evidence/vcs-state paths (`.coding-hermes/`, `.gitreins/`) ships no product behaviour and is bookkeeping despite its conventional prefix — a merge-brief subject routinely describes a host-level change (a systemd drop-in, a live config edit) while the commit it heads carries only the evidence file. `git show --stat <sha>` the material-looking commits before reporting them as product movement or unpushed product work, and use the same path-filtered diff (`origin/main..HEAD -- <product paths>`) before calling a local-ahead checkout a product divergence.

Resolve the prior certified SHA from the rolling row's STRUCTURED field and cross-check it against the append-only note in the same read. The row accumulates history in `foreman_note`, which appends: a later pass routinely certifies a new candidate in prose and never rewrites `detail.candidate_sha`, so the two disagree and either one read alone yields a wrong baseline for the product-path diff. When the note names a newer certified SHA than the structured field, treat the newer one as the prior candidate, compute the delta from it, and state in the record that the binding was stale and is being repaired — do not silently carry the older SHA (the diff then re-reports commits a prior pass already measured) and do not rewrite the note to match. Repair the structured field in the same carrier as the pass record, moving candidate, tip, census, CI ids, evidence commit and artifact digest together, and name the pass number so the next reader can order the notes.

Keep AUTHORIZATION and READINESS as separate blocker classes, and read the canonical cut-contract row before writing either. A minor (or patch) cut is frequently already authorized by an earlier owner ruling recorded in the pending cut-contract row, so a pass that restates it as "owner-gated" manufactures a blocker every later pass then honors. Carry the cut-contract row id in the rolling row's blocker list, and state in one line which mechanical gates hold the cut, so the record cannot be read as "waiting on permission" when the real block is a red gate, an empty publish channel, or a moving tree. Order the ordered blockers by the driver's OWN gate order, read from the script, not by inheriting the previous pass's list: mechanical preconditions (a missing notes artifact, an unbuilt dist tree) routinely refuse several gates BEFORE the authorization check, so a report that leads with permission buries the one blocker a worker can close — quote the refusing line and say which check fires first. Re-ordering is the finding worth reporting when it is the only thing that moved between passes. A carried RECOMMENDATION from an earlier pass is neither a blocker to re-file nor work to dispatch: re-test its URGENCY against the gate order on every pass, because a dominant earlier gate or an owner decision can leave the recommended split buying readiness rather than an earlier cut. When it does not move the cut, append ONE audit event on the owning row recording the re-test and why the split is deferred — do not mint the split row (a worker dispatched at it lands work no gate is waiting for, and the row then reads as progress), and do not restate the earlier ask in the new artifact as though it were this pass's finding. Say in the report that the earlier recommendation was re-examined and deferred, naming the gate that dominates it, so a reader sees a decision instead of a repeat.

Bind every CI, GitReins, dogfood, artifact, and version claim to the exact candidate SHA. Prove a verdict's candidate binding before crediting it, and prove ABSENCE the same way: grep every `.gitreins/history/*/*/verdict.json` for the full 40-character candidate SHA — no hit means no candidate-bound judgment exists, whatever the board status or a newer bookkeeping commit implies. A red, absent, skipped, or unproven exact-SHA gate blocks the cut. Never transfer an ancestor verdict without an independent product-tree identity proof and evidence-store binding. Dogfood binds the same way and is the gate most often miscounted as coverage: a battery directory whose own index declares the HEAD it measured is bound only when that HEAD is the candidate or an ancestor with a ZERO product-path delta to it, so run `git diff --name-only <battery-head> <candidate> -- <product paths>` and, when it is non-empty, cite the battery as N paths stale with its findings still pending. A battery that exists, is indexed, and is named in the board is not a receipt for the tree that would ship. Binding alone does not make a verdict a product receipt: read its SCOPE in the same breath. A `passed` verdict bound to the exact candidate SHA whose tier1 steps are `[guard]` only — lint and tests skipped because nothing was staged — certifies the guard and says nothing about the tree, so a cut resting on it rests on nothing. Quote the executed step list plus the tier2 status whenever a verdict is cited as gate evidence, and treat guard-only as UNMEASURED, not as a green. Distinguish PUBLISH gaps from DEPLOY gaps. A local artifact build is strategy evidence unless its embedded revision, version, and clean provenance are verified. Reconcile board status against ancestry before the decision: a pending row whose code is already an ancestor of the candidate is a reconciliation gap, and a stored FAIL verdict on a landed commit blocks the cut. When a board-only carrier advances the tip, do not treat the carrier as a new product candidate: bind the product decision to the last measured product SHA and bind the carrier separately to its own exact-SHA CI. A carrier with no matching hosted run is PENDING/UNVERIFIED, not green by inheritance from the earlier candidate. A completed row covering the same defect class is not standing coverage — re-measure the live numbers, and file a recurrence citing the closed row's closing numbers when the gate is red again.

A probe that answers "this surface is disabled" is UNMEASURABLE, not clean: a dependency-alert API refusing with 403 because alerting is off in the repository, a scanner that cannot run, or an empty feed on a repository with no alerts enabled must be reported as a named standing-coverage gap with its exact refusal, and filed as a row for whoever owns that surface. One refusal is not a row: a forge API answering 403 because of the repository's PLAN tier (private repo, "Upgrade to GitHub Pro" for rulesets or branch protection) is an owner purchase decision, not worker-executable work — name the invariant as UNMET and UNMETERED in the artifact, state that it was deliberately left unfiled, and do not hand a foreman a row it can only close by spending the owner's money. Silence here is read later as "no vulnerabilities found", which is the opposite of what was measured. Inventory repository-owned release tooling before fallback commands. Exercise the repository's own release path, and use its READ-ONLY dry-run as the gate PROBE when no cut is authorized — but only when a dry-run exists: a release script whose first act is to rewrite the dist tree and which offers no dry-run mode is CITED (script path plus its gate inventory), never invoked from a verify-only pass, because running it mutates the tree you are certifying: the refusal line names which check refused and at what value, which is the receipt for the unmet precondition — but read that from the message and never from `$?`, because a preflight piped through `tail`/`head` reports the PIPE's exit status, so a refused cut then prints `EXIT=0` and reads as a pass. A refusal is a FINDING only after the tooling's own residue is excluded: cut drivers commonly gate on a clean working tree while the harness's runtime state (review/verdict state, session caches) sits untracked and outside `.gitignore`, so the refusal names dirt the release does not care about and masks the gate that actually holds the cut. Peel it before writing any blocker — apply the script's own predicate to `git status --porcelain`, move the runtime paths aside, re-run the READ-ONLY dry run to reach the first genuinely unmet gate, restore them, and report THAT gate — then file the false positive as its own row with a RED-CONTROL acceptance: the exemption must still let a real source edit trip the gate, and any tracked config living beside the ignored runtime state must stay tracked. The peel is itself a mutation of a shared tree and can be REFUSED — moving another lane's runtime state is a consent-gated action even when the paths are untracked harness residue. A refused peel is a NON-CALL: do not retry it and do not reach the same tree state by another route (a stash, a scratch worktree with those paths absent, an orphan commit of them), because the refusal is about the mutation, not the command. What you then owe is an honest three-part blocker rather than a softened one: the driver's refusing line and exit status, the exact untracked paths that trip it, and an explicit statement that every LATER gate was NOT reached by this invocation, citing the previous pass's reading of those gates with its date instead of asserting they pass or fail now. Keep the red-control acceptance, and name the peel itself as the unverified leg in both the row and the artifact, so the next pass re-measures the clean-tree gate instead of inheriting a clean-tree claim nobody observed. Do not reorder the blocker list to hide the refusal either: the residue gate still fires FIRST and still blocks the cut, whatever the now-unmeasured gates behind it would say. A cut attempted right after any guard or judge run otherwise dies on a misleading message, and the next pass inherits the wrong blocker. The release OBJECT is part of that path, not just the tag: a cut script that opens the forge release leaves the auto-generated body, which is a commit dump rather than release notes — replace it with the curated notes file, commit that file, and re-read the release object afterwards. And re-derive a PRE-EXISTING dated changelog section against the release range before cutting, because an existing heading silences the driver's own note-completeness refusals while later commits go unannounced (`references/changelog-prep-driver-cut.md`). Never tag or force-move a tag on red or nonterminal CI without explicit owner override. First publication to an empty distribution channel requires explicit authorization. The authorized cut itself can still be hardline-blocked at the command scanner as a force-push false positive even though the push carries no force flag — the block is content-scan policy, not git policy — so when the identical PLAIN push is the sanctioned cut route, execute it through the documented blocked-command procedure (staged script / hermes-gateway-command-blocks), prove the remote accepted it as a NEW ref (`git ls-remote --tags`), and disclose the route plus the block text in the cut artifact. An empty channel also means the tag-triggered publisher is UNPROVEN rather than waiting: count the runs it would have produced (`gh run list --repo <org/repo> --limit 100 --json event,headBranch --jq '[.[]|select(.event=="push" and (.headBranch|startswith("v")))]|length'`) and when that reads zero, say plainly that the publish path is code nobody has executed — the green product runs certify the tree, never the publish step, so the authorized first cut carries the publisher as its own risk line instead of inheriting green.

Separate a PUBLISHER red from a PRODUCT red before calling a cut blocked. When the release/upload workflow dies in its own preflight (token permissions, zero product steps executed) while the CI workflow is green on the same exact SHA, and the repository documents a manual publish path that previous releases actually took, the invariant "exact-SHA hosted CI green" still holds: cut it, publish through the documented path, and state the distinction explicitly in the readiness artifact — naming the green product run, the failing publisher run, and its preflight cause — so the record cannot be read later as "released on red CI". A publisher that cannot run is a finding to file against the token/permission owner, not a product verdict.

A deploy-acceptance criterion phrased as a bare probe result — restart proof = the health endpoint returns 200 — is environment-coupled whenever that endpoint also reports a third-party provider. Separate the daemon from the provider before calling a deploy red: a bound listener (`ss -ltnp` naming the serving pid), a live process, and sub-100ms replies on TCP and on the project's unix socket prove the service is up, so the slow leg is the provider, not the build. Read the payload for its own labelling: a timeout figure the body calls a health-probe budget and distinguishes from the client query timeout is a probe budget, and a degraded status carrying it is an operator fact, not a product regression — never carry it into the cut decision as if the build were bad. Also prove the measurement was taken on the deployed build and not a stale process: the artifact mtime must precede the unit's `ActiveEnterTimestamp` and `NRestarts` must be 0, or the probe describes the previous binary. A version string carrying a dirty marker (`-dirty`, `-modified`, a `+dirty` suffix) reports the BUILD CHECKOUT's tracked-file state, not the deployed artifact's: a build embeds `git describe`/`git status` from whatever tree it ran in, so one sibling's tracked edit to a runtime cache (`.gitreins/` state, a review/verdict cache) stamps an otherwise candidate-exact binary, and the deploy gate then fails on the marker rather than on staleness or source integrity. Attribute it to the shared checkout, name the dirty path from the build receipt, and when the gate genuinely needs a clean string rebuild from a detached worktree at the candidate SHA — never revert a sibling's tracked file in the shared tree to clear the marker. Staleness itself is a PRODUCT measurement: when the deployed build predates the candidate, run the product-path diff between the deployed build's commit and the candidate — zero paths means the deploy is already equivalent to the candidate however many bookkeeping carriers landed in between, so report equivalence with the diff receipt rather than a staleness finding. Sample that endpoint at least twice inside one pass and report the SEQUENCE, never the last reading: a provider-coupled health field can answer degraded, then healthy, then degraded across twenty minutes on a byte-identical tree with an unchanged pid and uptime rising continuously, so a single sample recorded as the gate state is re-read by the next pass as a regression or a fix that never happened. A contradicting repeat on an already-filed row is corroboration — carried in that fire's record and named as measured-but-not-refiled — never a new row and never a new carrier.

When a downstream row's stated criterion literally reads `HTTP 200` and the degraded payload makes that unobtainable for reasons outside the product, that is the criterion-cannot-pass case above and it is an EVENT on the owning row, not a new row: append the audit event naming the endpoint, the probe budget, what would count as pass, and the acceptable reshaping (liveness/readiness split, provider probe excluded from the status field, or the criterion amended) — the row's owner already holds the fix, and a dispatched worker on the current wording restarts a healthy daemon and still misses. Whichever reshaping lands must be shown reachable in BOTH directions on one build: a probe returning 200 and a probe returning the degraded payload. Never relax the criterion yourself to make it green.

## Re-fires and delivery

A re-fire over unchanged product paths carries measurements but must name both the certified SHA and current tip. When an earlier firing of the SAME tick already published the release, the pass owes no new decision and mints none: re-derive the release layers live instead of quoting the cut-time record — the tag object and its peeled commit from the remote, every asset re-downloaded and re-hashed against the release's own `SHA256SUMS`, the release object's draft/prerelease/asset-state fields, and the published body. A Release that publishes no checksum asset leaves nothing to verify AGAINST, so re-hash every asset anyway and compare with the digests the cut recorded in the row or artifact: a byte-for-byte match is the receipt, and when no recorded digest exists you say the assets were re-hashed but not matched, rather than reporting a checksum verification that had no reference. Hash the body from a fetched release object with `jq -j .body`; `gh api --jq` (and `gh release view --json body`) emits a trailing newline, so a shortcut hash can never byte-match `docs/releases/<tag>-notes.md` and manufactures a false mismatch. Two further false mismatches come from the same family. `-j` IS the shorthand for `--jq`, so a command written `--jq -j .body` hands that flag two arguments, prints nothing, and reports the EMPTY string's hash as a body difference — fetch the release JSON to a file and run `jq -j '.body' <file> | sha256sum` on it. And `jq 'length'` on a string counts CHARACTERS while `wc -c` counts bytes, so a body carrying any multibyte character reports a length difference on text that is byte-identical; compare hashes on both sides, or counts of the same kind. State in the record that no new cut was minted, so the re-derived numbers are not later mistaken for a fresh release. Reuse the canonical rolling row; do not mint duplicate release rows. Write each re-fire as a dated DELTA section appended to the same committed artifact: a short table of only the surfaces that can have moved (parity, exact-tip CI run id, product-diff file count, commit census, tag/release inventory, deployed probe) with the previous fire's reading beside the current one, so a reader sees what changed without diffing two documents — never restate the full report, and name explicitly which readings FLIPPED (a probe that answered 200 last fire and answers degraded now) instead of listing values flatly. Commit the delta section in the same carrier as the row write — but only when a reading CHANGED. The delta exists to show a surface that moved (a leg that concluded, a run that registered, a gate that flipped, a prior `INTERIM/PENDING` that resolved), never to restate a re-read that returned the previous fire's values. A fire whose every reading is identical to the prior fire's mints NOTHING: no artifact, no row, no carrier, and its record is the memory key alone. A fire whose numbers live only in scratch or the transcript has to be measured again. Let the readings decide what to mint, not the fact that the tick fired — a lane that appends a delta per fire over a byte-identical product tree compounds into a carrier chain of no-op pipeline runs, and that chain is itself re-read later as evidence of work that never happened. If the tip moves materially, re-census. If it moves only through bookkeeping, re-anchor candidate, artifact, and CI provenance without relabelling old measurements as fresh.

Establish WHICH fire this is before measuring. Enumerate the lane's memory KEY PATHS first (`list_keys` with `prefix: "/"`, `maxDepth: 2-3`) and match the tick id inside the paths: an exact-key lookup does not need the semantic index, and a per-tick family such as `/releng/ticks/<project>/<tick-id>/pass-NN` hands you the pass ordinal directly. Reach that family through the STORAGE path (`list_keys` at a depth deep enough to show the per-fire keys — the fourth component carries `pass-NN`, so `maxDepth: 4` where 2-3 stops at the tick directory — then one SQL projection over the memories view), not the semantic one: a degraded embedding leg answers `recall`/`search` with a timeout that consumes the whole tool budget and returns nothing usable, so cap that leg at ONE attempt per fire and treat the timeout as an UNMEASURED read — never as an empty ledger, and never as licence to call the pass a first fire. The memories view has no `content` column and `DESCRIBE` is refused as non-SELECT, so read a fire chain with `SELECT * FROM memories WHERE key LIKE '<prefix>%'` and take the decision from `attributes` plus `embedding_text`; `json_extract_string(attributes,'$.fire')` projects the discriminator directly. A DUPLICATE INSTANCE of your own tick (not only a sibling lane) is the common shape: while you measure, another instance can land its key minutes after your pass started, so enumerate the family **before the FIRST mutation of the pass — the first artifact append, the first row note, the first carrier — not merely before the memory write**, and name your fire suffix from what you find; overwriting or minting beside an existing same-tick key produces two narratives for one decision. Enumerating only at memory-write time is too late: the artifact and row are already published, so a fourth-or-later fire that should have carried-only has minted two carriers and must then spend a correction carrier on its own wrong ordinal. Count the discriminator keys (`pass-NN`, `pass-NN-fireb`, `pass-NN-firec`, `pass-NN-fired`) rather than the `-fireb` suffixes alone — the fifth fire is `-firee`, and a family that already reaches `fired` means your pass mints nothing at all. Match the family's OWN suffix shape instead of imposing this example: a family whose second fire is `pass-01-refire` takes `pass-01-refire-b` for the third, and minting `pass-01-firec` beside it splits one tick's chain across two naming schemes that no later pass enumerates as one. Two signs that a family has ALREADY drifted, both reconciled rather than trusted: a fire filed under a SECOND subtree of the same namespace (a tick-scoped `/project/<p>/release/<tick>/pass-NN…` beside a lane-styled `/<lane>/release/readiness-passNN-<date>`), and a record whose `fire` attribute disagrees with its own key suffix (`pass-01-refire-b` carrying `fire: pass-01-firec`). Read every candidate record before deciding the ordinal — the stray subtree often carries the only committed board commit and CI run id — take the ordinal as the highest dispatch number either surface names, and keep writing into the tick-scoped subtree so the next pass enumerates one chain. The tick id's clock component never decides the ordinal — it can carry a different offset from the fire's own wall clock, so an ordinal read from it either re-runs a delivered pass or calls a first fire over a chain that is already three deep; the key family plus the committed rows are the ordinal. One prefix recall over the lane's own memory keys, matched on the tick id (`references/tick-double-fire-and-judge-failover.md`, and `references/refire-measurement-and-evidence-carry.md` for where that family actually lives — it is not always the `releases` namespace: resolve it from the PROJECT's own ledger first, a namespace named after the project, then `releases`). Pass `namespace` explicitly on every read and write — the connection carries a host-level default that is usually some OTHER project (`currentNamespace` in the namespace listing names it), so an unscoped `list_keys` answers from the wrong ledger and returns an empty list that looks exactly like a first fire. Confirm the namespace in the listing before measuring, and treat the returned list's emptiness as UNMEASURED until the namespace is proven correct, tells you whether an earlier pass already recorded the decision — a third-or-later fire over an unmoved product tree re-derives only the surfaces that can have moved, writes its record under an explicit fire suffix, and mints no artifact, row, or carrier. Measuring first and discovering the prior records afterwards is how a lane produces a second narrative that contradicts its own ledger. An EMPTY ledger recall is not proof of a first fire: prior fires routinely land their artifact and row and never mirror the decision into memory, so before calling a delivery pass one, enumerate the board evidence directory for files carrying the tick id (a `-fire-b`/`-fire-c` suffix is the tell) and the rows' `detail.evidence[].run_id` timestamps for that same tick. The cheapest ordinal on a JSONL board is one grep for the raw tick id — `grep -c '<tick-id>' .coding-hermes/board/tasks.jsonl`: a hit means an earlier fire landed a row, and that row's `foreman_note` names both the tick and the commit it delivered, which is the fire-ordinal receipt to quote; check with `git log` whether that commit is already an ancestor of the tip, since the row's `updated_at` alone does not say what landed. Read that number as ROWS, never as fires: one fire routinely files three or more rows under the same tick id (one for the decision, one per completion, one per finding), so a count of 3 is a single fire's row batch and calling it a third fire invents two passes that never ran. The ordinal itself comes from the delivery channel plus carrier ancestry; the row count proves only that at least one fire landed. Write the missing record under an explicit fire suffix and say plainly that the earlier fires left no key; append the current decision, never backfill their records.

An EMPTY memory recall is not a first fire. A lane that only records at close-out leaves no key behind when its pass was interrupted, so corroborate the ordinal from the delivery channel before deciding a cut is due: `gh release list --limit 5 --json tagName,publishedAt`, the release's asset timestamps, and the rolling row's `updated_at`. Any of those landing inside the current tick window means an earlier firing of THIS tick already delivered — classify the pass as a re-fire and carry, whatever the ledger says. Where no release has ever been published the channel check cannot order the fires at all, and the artifact lineage is then only a LOWER BOUND, never the ordinal: `git log --oneline -- docs/release-evidence-*` returns one commit per pass that MINTED something, while a carry-only pass over an unchanged product tree correctly mints nothing — so ten fires of one tick can leave six evidence carriers and reading the lineage as the pass count under-counts by four and mislabels your own fire. Take the ordinal from the ledger key family (§2a below) and quote the git lineage only as proof that at least that many passes existed. Normalise the tick id's time component before declaring a new tick — it recurs both hyphenated and collapsed (`HH-MM-SS`, `HHMM-SS`), and reading the two forms as different ticks launders a re-fire into a first pass. Run that channel check BEFORE the semver decision, because the failure it prevents is proposing a second cut on a tree whose release is minutes old, which then reads as a duplicate tag attempt rather than a carry.

Classify the tip movement BEFORE running the semver census. First resolve the prior certified SHA from the committed artifact or row, capture the current tip once, and run one product-path diff: `git diff --name-only <certified-sha> <tip> -- . ':!releng' ':!.coding-hermes'`. Zero paths means the product tree is unchanged: do not recount Conventional Commits, rebuild artifacts, rerun product gates, or manufacture a new release decision. Carry the prior product measurements with both SHAs, then re-check only surfaces invalidated by the bookkeeping tip (exact-tip CI, board/artifact persistence, tags/releases, and any carrier identity). A nonzero product-path diff is the only trigger for a fresh semver census and product-gate run. This ordering prevents a board-only carrier from being misreported as a new patch/minor candidate.

Decide "unchanged product paths" with one product-path diff, not a tree crawl: `git diff --name-only <certified-sha> <tip> -- . ':!releng' ':!.coding-hermes' ':!reports'`. Include the lane's own evidence tree in the exclusion set: a project that keeps its sweep report outside `releng/` (commonly `reports/verification/`, `docs/release-evidence/`, or a per-tick `docs/releases/<tick>.md`) otherwise shows one changed product path on every re-fire, because the previous pass's report is always inside the delta — that is bookkeeping, and letting it count as material forces a re-census that owes nothing. Re-derive the exclusion set on EVERY fire and keep every entry STRUCTURAL (board tree, vcs-state caches, readiness/evidence trees, named carrier paths): a path excluded because it was transient untracked residue becomes a real product path the moment another lane commits it, so a carried exclusion silently hides a product move and publishes a false zero. When a path graduates out of the excluded set, report it as a measured product change with its commit, even when it is docs-only and version-neutral. Zero paths means the verdict is carried, not re-decided — record it in release memory and mint no artifact, no readiness row, and no carrier for an unchanged verdict. A finding measured fresh on such a pass that has no product impact and no failing gate — remote-branch exposure, fully-merged branches nobody reaped, dependency lag behind a gate that still passes — belongs in that fire's memory record with its exact counts and stays off the board: filing it buys a carrier for a verdict that did not move, and the board already carries the rows that actually gate the cut. Say in the report that it was measured and deliberately left unfiled, so a later pass does not read the silence as "nobody looked". A non-empty product diff that collapses under `git diff -w --stat` is formatting-only: non-material, so no re-census and no semver change is owed, but the suite is a claim about the SHA you name, so re-run it through the repository's own interpreter (`.venv/bin/python -m pytest -q`); collection errors under the system python are a missing-dependency environment, not a repo defect. The same diff proves a BOOKKEEPING CARRIER is bookkeeping-only, and there the exclusion set must be named rather than blanket: enumerate the carrier's own paths (`git show --stat <carrier>`) and clear only the readiness/board trees it actually added. A blanket `':(exclude)docs'` hides a real product change in a project whose docs ship with the code, and the proof then reads as evidence it never examined.

In a shared checkout the tip can advance BETWEEN your measurement and your carrier push, so a no-cut pass is not finished at commit time. Re-read `origin/main` immediately before the push and again after it. If it moved, classify the delta and, when the record you just pushed names a candidate that is no longer the tip, append ONE audit event re-anchoring candidate, delta class, and the fresh suite receipt at the new SHA. Classify that delta by SHIPPED paths, not by commit count: sibling commits that only add repository scripts no deployed binary executes (probe/ops helpers, evidence tooling) leave the product runtime tree unchanged, so the census and every gate arm carry verbatim and the record gains a reconciliation block naming both ranges and the product-path diff that proved zero runtime change; a changed shipped path re-opens the census instead. Never amend an already-pushed carrier to absorb the reconciliation — siblings cite the published bytes; write it as its own commit and say in the message which candidate SHA the carried measurements belong to. That correction is the only second carrier a no-cut pass may mint — it replaces stale evidence, where a bookkeeping-only advance must mint nothing.

The reverse direction costs just as much: a sibling lane can commit the SAME board file you just appended to, and when its commit re-serializes the JSONL wholesale it ABSORBS your uncommitted row. `git status` then shows that board clean, your row lives inside a commit you did not author, and a pass that trusts its own working-tree diff either re-appends it (duplicate id) or reports a row it believes it never filed. Before staging anything, reconcile the write side: `git log --oneline origin/<branch>..HEAD`, `git show --stat <sibling-sha>` for the board paths, `git merge-base --is-ancestor <your-baseline> HEAD`, and `git rev-parse HEAD` twice a couple of seconds apart to see whether it is still moving. Then prove your row in THEIR committed tree — `git show <sha>:<board>/tasks.jsonl | grep -c '<ROW-ID>'` plus a readback of its full key set and acceptance fields from that same tree — and re-run the board validator on the committed state, because a wholesale re-serialization is exactly the edit that can leave the board invalid while every diff looks like bookkeeping. Your `git add -- <path>` is now a no-op and the carrier carries only your artifact; say in the commit message that the sibling commit absorbed the row, and leave their commit untouched — extracting your row with a reset, amend, or revert rewrites bytes a sibling may already cite, and re-serializing to "own" the row is what produced the collision.

When the tip advances mid-pass, the artifact owes a dated correction section that SCOPES every "unchanged" claim to the interval actually measured (`<baseline>..<measured-tip>`) and names the advance with its commit, its exact-SHA run id, and its changed-path count. An unqualified "the product tree did not move" is true only of the window you measured and becomes false the moment a sibling's product commit lands — and it is the sentence the next pass inherits as the reason it need not re-census. Carry a per-SHA CI line for EVERY tip the window passed through (each run bound to its exact `headSha`), not just the current one, so the earlier legs stay valid receipts instead of being re-derived. If the carrier is not yet pushed, fold the correction into that same artifact before committing and let one commit state the scope; if it is already pushed, own commit, never an amend.

Write the final evidence artifact, push it, and read it back before composing the board carrier. Freeze the exact report after all counts and receipts are final. The scheduler's configured report link is the normal delivery; a direct delivery is one compact decision line plus the link — unless the tick brief itself names the delivery contents (a decision line plus an evidence table, one row per surface), in which case the brief wins and the table is what ships. On a plain-text surface (api_server, CLI, messaging) render that table as aligned plain text, one row per surface with its measured value and no markdown pipes or header rules, because a pipe table arrives as unreadable noise where markdown is not rendered. If carrier CI is pending, explicitly label the report `INTERIM/PENDING`.

## Local-CI gate when hosted CI is unavailable

When hosted CI cannot run (billing block, outage), the gate is a LOCAL REPLICATION of the CI workflow on the exact candidate SHA, only with explicit owner override. First classify the failure: `gh run view <id>` — jobs "never started / payments failed" is NOT a red gate (zero executed steps, nothing to re-run); a red gate means executed steps failed. Then replicate every workflow step locally in order (build, vet, full `go test ./... -count=1`, lint, secret scan) and keep the log as the gate receipt. Disclose the substitution IN THE TAG MESSAGE (which workflow was blocked, that the local battery is the gate, where the evidence log lives). Publish via local GoReleaser, not Actions: `export GITHUB_TOKEN=$(gh auth token)` and `unset GITLAB_TOKEN GITEA_TOKEN` first — goreleaser aborts in 0s with "multiple tokens found, but only one is allowed" when a second forge token sits in the environment. Verify the published release after: assets non-draft, `sha256 --check checksums.txt` on downloaded artifacts, and the binary's self-reported version/build matches the tagged SHA.

## Closing a red the lane is permitted to fix

Verify-only is not re-file-only. When a blocker that previous passes kept filing is a red gate on code you can attribute, a bounded fix inside the wave budget — worktree per fix, worker dispatched, real-runner proof — is in scope, and filing the same finding again does not move the release. What the lane lacks without the owner is version and publication authorization, not the right to clear a red gate.

The budget is for clearing attributable reds, not for re-doing work another lane already holds. When every remaining blocker is an owner decision, an unbound evidence gate, or a pending row the foreman owns, dispatch nothing and report the budget unused WITH that reason: an unspent budget explained is a decision, an unspent budget unexplained reads as an idle tick, and spending it on an already-pending row is a duplicate dispatch at the same file. Doc-hygiene items that a cut would absorb — a version stamp, a dated changelog section — stay untouched when the cut is unauthorized, because landing them alone makes every build from the default branch advertise an unreleased version; carry them as unmet preconditions plus the single action that completes them.

When the lane may not merge (satellite boundary), the deliverable is a PUSHED BRANCH, not a landed fix: push it, re-run the full gate battery at the branch head, and keep the row pending with merge plus post-merge re-run named as the remaining acceptance in the field the writer actually populated. Never close a row on an unmerged branch, and never describe a pushed branch as landed work. Classify a `govulncheck` non-zero that names `Found in go<x>` / `Fixed in go<y>` as TOOLCHAIN-PIN LAG, not a dependency defect: a closed vulnerability row does not stay closed when a newer stdlib advisory overtakes the pinned toolchain, so it is a recurrence to file, not a regression to argue. Bump the `go` directive and every Dockerfile/workflow pin in the same commit, and prove the clean scan in a throwaway probe worktree FIRST (one sed, one run, minutes, no worker round-trip); dispatch a bounded worker only for the mechanical multi-file edit, once the fix is known to work.

A dispatched fix is a CLAIM until the lane re-runs it. Re-verify on a throwaway clone of the worker's branch (`references/changelog-prep-driver-cut.md`), never by reading back the worker's own receipts: the fix either makes the previously impossible state succeed or it does not. Re-run the PRE-FIX driver against the same input as well, so the record carries a fail-first arm and a fixed arm instead of a green of unknown provenance — offline unit tests can be green on a script that is still broken. When the fix adds or changes a probe that resolves "which SHA does this gate bind to", expect it to name the FIX COMMIT once that commit exists: a resolver pointing at its own commit is correct behaviour, not a contradiction of the reading it gave at the pre-fix tip, and on a repo whose CI runs are path-filtered there is no other honest answer. State the tip each reading was taken at.

When a matrix red has more than one root cause, land ONE CAUSE PER BRANCH first: each branch proves its fix by leaving exactly the other cause's tests as the remaining reds on the real runner. Combine with a cherry-pick PR only after both isolation runs are observed, merge with `--merge` so each fix stays individually attributable, and close the isolation PRs citing the merge commit. The receipt for a landing is the gate job green on the MERGE COMMIT (legs named), never the PR head and never a bare top-level success; a non-gate job still running at merge time is disclosed as in flight, not waited on.

A judge that FAILs a new test for being non-discriminating on the judging host is right even when the behaviour is fixed on the failing platform. Read the test, confirm the mechanism, file the test-rigour row for an injectable OS/env seam, and leave the parent row OPEN with a note that the behaviour is proven and the guard is not. Rewriting the criterion so a re-judge passes converts a real gap into a false green.
