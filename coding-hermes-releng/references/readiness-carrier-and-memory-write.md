# Readiness carriers and durable writes

Use this procedure for release-readiness sweeps that create evidence and board state.

1. Bind the measured product candidate to the full SHA of the exact default-branch tree. Keep three identities separate: the tested product candidate SHA, the evidence/artifact commit SHA, and the final board carrier SHA.
2. Write the evidence artifact inside the canonical owning checkout and hash the final bytes. If its directory is ignored by policy, force-add only that named artifact and verify `git ls-files --error-unmatch` before committing. Commit the artifact first. A readiness artifact in a detached worktree or scratch directory is only a measurement carrier until the identical repository-relative blob is committed.
3. Re-read the current board immediately before creating the row. Use the sanctioned writer, create exactly one matching event, and stage only the board paths. Read the row and event from the committed tree, not merely the working copy.
4. Push the carrier and verify remote parity. Query hosted CI by the carrier's full SHA. Never copy the candidate's green run into the evidence or board carrier fields; if the carrier has no run because it is intentionally skipped, state that mechanism and keep the candidate receipt separate.
5. Before final delivery, re-fetch the remote board blob and verify the exact row, matching event, evidence path, and evidence hash. Check that the row's candidate, decision, carrier, and latest evidence entry are the current pass—not merely that the foreman note contains them. If the carrier CI is learned only after the planned push, keep it as a separate delivery receipt rather than creating an unbounded second carrier solely to restate it. Treat a successful writer or push message as transport evidence only.

For deferred memory or app writes, construct the complete payload before invoking the tool: explicit leading-slash key, resolved namespace, closed domain, attributes object, string content, and author where supported. A missing-required-argument response means no write occurred. Stop after that response, correct the actual payload once, invoke once, and read back the exact key through the provider's read tool. Never retry `{}` or partial payloads: repeated validation failures create noise without durable state and can make a release report claim a memory receipt that does not exist.

Resolve the namespace from its own KEY HISTORY, never from a name pattern. Project memory is routinely duplicated — a bare `<project>` namespace holding the real tick records beside a `coding-hermes-<project>` mirror holding one or two stale leftovers (or the reverse) — so list the candidate namespaces, then `list_keys` on each, and write where the convention actually lives. Follow the key shape you find (`/project/<project>/<lane>/<date>-<topic>`) instead of inventing one: a new key in the wrong namespace is invisible to the next tick, which reads the populated one and re-derives the decision you just recorded.
