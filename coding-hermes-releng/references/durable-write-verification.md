# Durable write verification

Use this procedure for release evidence, board rows, audit events, and memory records.

1. Build and inspect the complete serialized payload from the writer schema before invoking it. Include every required field, set the target namespace explicitly, and preserve exact identifiers and strings. A wrapper call with `{}`, omitted arguments, or an unscoped namespace is not a valid probe.
2. Validate locally when possible: parse JSON, require the expected row/event shape, and check that the key or task ID is unique before appending.
3. Treat schema rejection as a non-write. Do not retry the unchanged payload; correct the missing or malformed field once. If the caller emitted an empty wrapper invocation, stop that write leg rather than repeating `{}`; only a visibly populated direct payload can qualify as the one correction attempt.
4. After a successful write, read back the exact key, row, or event from the authoritative store and compare the stored content to the intended payload. For a board update, verify both the working-copy row/event and the committed remote-tree row/event after push; compare the rolling row's structured binding with the new event when the pass is a re-fire. Then query hosted CI for the carrier commit's full SHA and poll any resulting run to completion before calling the delivery closed. A local artifact or sender success line is not persistence evidence.
5. If the writer is unavailable or readback cannot be completed, label persistence UNVERIFIED and keep the evidence artifact explicitly unpublished. Do not claim the board, memory, or decision record was saved.
6. For append-only JSONL, verify every physical line parses, the new ID is strictly above the prior maximum, and the diff is one append rather than a broad reserialization. Count as well as parse: the file must grow by exactly the number of records the pass claims to have added (`wc -l` before and after), and a `select(.id=="<new-id>")` against the WRITTEN file must return the row. A generator that builds a new row object but never appends it to its output list still prints its success line, still exits 0, and leaves the file byte-identical — so the writer's own report is transport evidence and only the count delta plus the id select prove the append.

A half-applied board write is repaired by rolling back, not by re-running on top. In a dedicated detached write worktree that has no other dirty paths (`git status --short` first), `git checkout -- <board files>` restores the fetched board and the corrected script then runs clean; re-running the fixed generator over the partial output appends a second copy of every event it already wrote while leaving the row you were fixing still wrong, and the duplicate events are not removable afterwards without another carrier.

Project board rows from the committed tree after the carrier commit (`git show <carrier>:<board/tasks.jsonl> | jq`), not from the working file or from the remote default branch: the hook that gated the commit ran on the staged tree, the working copy can still carry a sibling's later edit, and the branch can advance past your carrier mid-pass. Read the row out of the tree you actually pushed.

Continue ONE key per tick across passes. A later pass of the same tick appends another record to the existing key (recall it first, then write again) instead of minting a per-pass key: the key family is how the next reader reconstructs the tick, and a key per pass scatters it. Verify the append by the returned id being the newest record for that key, and keep `attributes` consistent across passes (same field names, same units) so a reader can diff pass N against pass N-1.

When the FIRST memory write for a tick happens on a re-fire (earlier passes delivered without a record), mint the base key with NO pass suffix — `<family>/<lane>-<tick-id>` — so the record for this pass is also the key later passes append to. Embedding the pass number in the key that opens the family guarantees either scatter or a rename later. Discover the sibling shape once before minting: one bounded `list_keys` with the family prefix (and one at `/` in the namespace) shows the house convention for the PREFIX and its field shape, so the new key reads as a member of the family rather than a one-off. Never let a `<family>/…/pass<N>` sibling define that convention: per-pass keys are the exact defect this rule prevents, so a store already holding `pass11`/`pass17` is a fragmented family, not a house style. Mint the base key for this pass, say in the record that earlier passes used pass-suffixed keys and the family is scattered, and do not mint `pass<N+1>`. The no-suffix rule is not confined to re-fires: a NEW tick's first record also takes the bare `<family>/<lane>-<tick-id>` form. A family already holding `pass-12`, `pass-15`, `pass20` is evidence of the defect, not a house style to imitate — copying that shape because the tick id happens to be new produces `…/<new-tick>/pass-27` and re-founds the scatter under a fresh prefix, where the correct record carries no pass number at all. When several competing families coexist in one namespace (`/project/<p>/…`, `/projects/<p>/…`, `/releng/ticks/<p>/…`, `/releng/<p>/ticks/…`), extend the one whose path already carries this lane's tick-id shape rather than minting a new top-level prefix, and name the family you joined in the record.

A recall whose transport dies mid-call (the tool reports the underlying subprocess lost, not a schema refusal) is NOT a failed write and NOT proof of anything. Do not replay that call. Settle the readback with an exact-key recall, or with a key-prefix `list_keys` scoped to the namespace — both are single lookup paths that do not depend on semantic search — and report which one proved persistence.

A successful `remember` returns an id, key and partition. Confirm it at the namespace store — grep the returned id and key in `<namespace>/event/<YYYY-MM>/current.jsonl` (and the key registry beside it) and check the row is the newest for that key. Do this whenever an exact-key or key-prefix recall comes back empty: the query indexes can lag the write, and a `contains=` search can sit on its timeout instead of answering, so an empty recall is NOT evidence the write failed — and re-writing on that assumption duplicates the record. A `valid_from` stamped ahead of the read instant hides a stored record from current-time recall by design, so probe once with the historical/as-of flag before calling the leg lost: that read returns the full row and proves only the validity window was wrong. Report persistence as filesystem-verified and say plainly that the query leg was not the proof.

The namespace store can exist under MORE THAN ONE root on a host — a live/serving checkout beside one or more build, migration or write-test checkouts. Grep the candidate roots directly in a bounded loop of two or three known paths; never locate them with a filesystem-wide `find`, which burns minutes and returns nothing usable on a busy host. A zero-hit read in one root is not evidence the write failed — it means you read a root the writer does not serve, and re-writing on that assumption duplicates the record in the store that does. The serving root is the one whose partition contains the key `list_keys` just returned for this namespace, so list first, grep the roots, then call the leg verified. Cheapest existence proof after a write is a key-prefix listing scoped to the namespace (`list_keys` with the tick or date prefix): it answers in one call, returns per-prefix counts, and does not depend on embeddings, so use it for readback whenever semantic search is slow or unavailable — reserve search for content questions. An empty result is an answer about the QUERY, not the store: a `LIKE`-projected query that comes back with an empty column set, zero rows, or `truncated: true` proves nothing about absence — re-issue the same predicate without the `ORDER BY`/extra projections, or fall back to the namespace-scoped key-prefix listing, before recording "no prior record". `list_keys` with no arguments lists the DEFAULT namespace, so an unscoped listing that omits the project's keys is expected and is not evidence the family is empty; always pass the namespace and the key-family prefix. If a schema error or transport result shows an empty/unpopulated write payload, stop the write leg immediately; do not keep repeating list or recall calls that cannot validate a write which never occurred.

Common schema trap: deferred memory writers may require `key`, `domain`, `attributes`, and string `embedding_text` even when a shorter convenience form appears plausible. The two shapes carry the SAME facts under different names — the DuckBrain HTTP route takes `{key,domain,namespace,content}` in the body, while the MCP `remember` takes `content` nested as `attributes.content` with a separate top-level `embedding_text` — so a payload copied from the documented HTTP form is rejected for missing `attributes` and `embedding_text`. Build the payload from the loaded tool schema, never from the route contract you remember. Supply all required fields and use the intended project namespace; never silently fall back to a default namespace. Omit optional fields entirely instead of passing an explicit zero-value: a `null` for a typed optional (`validUntil`) fails argument validation at the wrapper while the absent key passes, and the refusal costs a dispatch without teaching anything about the store. A schema error is not permission to probe with `{}`: correct the named payload once, or mark the leg UNVERIFIED if the transport still drops it.

Read a record back by PROJECTING the fields you want out of the attributes map (`attributes->>'decision'`, `attributes->>'origin_main'`) against the store's own column names — `key`, `timestamp`, `attributes`, `embedding_text` on the memories view. Aliasing a column the view does not expose (`content`, `created_at`) is a binder error, and a mistyped projection that returns zero rows reads exactly like "no record was written", so dump a row's key set once before projecting anything you have not read live. When several structural rejections have already been spent on one writer, the deferred bridge may fail fast or answer with a truncated result; back off briefly and send ONE visibly corrected call rather than a burst of near-identical probes — a burst produces no new store evidence and consumes the pass.

Amending a field in a detail payload you already wrote — injecting `artifact_sha256` once the artifact is hashed — is an EDIT, not a script. Use the patch/write tool against the file. Inline interpreters (`python3 - <<'PY'`, `python3 -c`) are consent-gated on unattended surfaces: the call is refused after the wait and returns nothing, so a one-key change costs the tick. Write the detail JSON, hash the artifact, then patch the hash field in; never try to generate the file and its self-hash in one shell step.

A record's facts must be PROBED, not inferred from the shape of a neighbouring fact. The failure mode is writing a per-job attribute ("job X failed for reason Y") that no endpoint was queried for: the pipeline-level status looked sufficient, so the job-level cause was filled in from context, and a durable record then carries a cause the API never reported. Read the object that owns the field — the job endpoint for job status/`failure_reason`/`started_at`, the runner endpoint for runner state — before the attribute enters the payload; anything not read that way is left out of the record rather than described.

A JSON NUMBER is not an id carrier. Board and event ids are 19-digit integers, past 2^53, so any
layer that parses `attributes` as JSON round-trips `1794096919346399916` into `1794096919346396` and
the record then cites an event that does not exist. Pass long ids as STRINGS in attributes; when the
exact value is already stored as a number beside a correct string field, state in the record which
one is authoritative instead of leaving two spellings of one for a later reader to reconcile.

## Delivery ordering

Do not deliver a report before its evidence and board bindings are final. A sender success is only transport evidence; after sending, retain the message ID and do not edit the delivered file in place. If a later probe changes a claim, create a corrected artifact section or replacement file, re-hash it, update the board's complete structured binding, push and read back the correction, then send one explicit correction/addendum. This preserves a stable relationship between what the recipient saw, the digest in the board, and the final authoritative state.

An append-only store cannot be silently corrected. When a record is already written with a wrong attribute, re-write the SAME key with an explicit correction: name the wrong field and value, the probe (endpoint + observed values) that disproved it, and that this entry supersedes the earlier one. The wrong record stays visible forever, so an unflagged rewrite leaves two contradictory claims in the same key and the next reader cannot tell which is live.
