# Audit-family row verification (produced-artifact premises)

Board rows minted by audit producer lanes (deadcode / lint / typing / complexity / security gatherers) carry QUANTITATIVE premises — a violation count per repo in the row title. The premise is the gatherer's output artifact, not a repo state: verify against the artifact, and never re-run the gatherer to check a row (each run sweeps ~15 repos and regenerates the whole family's evidence).

## Procedure

1. **Locate the artifact.** Per-family JSON + TXT live under `~/.hermes/audits/`: `python-deadcode-audit.json`, `python-lint-audit.json`, `python-annotation-audit.json` (typing), `python-complexity-audit.json`, `python-security-audit.json`. One regen refreshes the entire family's rows.
2. **Freshness FIRST.** Read `run_date` / `generated_at` from the JSON and compare against the row's `created_at`:
   - Artifact regenerated AFTER the row was minted → re-derive the count from the CURRENT artifact before judging the premise. An apparent count mismatch is a stale number on the ROW side, not a false premise: the verdict is an evidence refresh on the row (update its cited count), never a retirement.
   - Artifact older than the row → the row was minted from a NEWER run than the on-disk artifact (producer may write elsewhere or a newer regen was cleaned); do not fail the row on the old artifact — note the artifact-age mismatch and verify the count by a cheap targeted re-run of the gatherer for that one repo if the row's cited command names one. The cited repo being ABSENT from the newest artifact is a third case: the gatherer caps its sweep at a top-N by python-file count (default 15, `PYAUDIT_MAX_REPOS` env), so a repo drops out when larger repos crowd it out — absence proves nothing about the row; verify by direct re-derivation (step 5) and name the cutoff mechanism in the evidence note.
3. **Verify by exact sum.** Match the count FIELD SHAPE of the specific family's artifact before summing — field names are NOT uniform across families, and they DRIFT across gatherer versions within one family: the typing/annotation artifact carries `functions_missing_return` and `args_missing_annotation` per findings entry (and `totals.functions_missing_return` etc. at top level), NOT `rule_counts`; the lint/deadcode/security/complexity artifacts carry `rule_counts` + `top_rules`, and entries may ALSO carry a direct total-style field (`total` / `violations` / `violation_count`) whose presence varies by gatherer version. `findings` is an ARRAY of entries (indices, not repo-keyed) — `jq '.findings | keys'` returning `0,1,2,3` is the normal shape, not corruption. Read `jq '.findings[0] | keys'` first and verify against the fields that actually exist, not the shape the previous family (or the previous cycle) used. Each entry also carries `repo`, `path`, and — on some families — `top_rules`. Sum the cited field for the cited repo and compare to the total in the row title — EXACT match proves the premise; a diff means the row cites a different generation than the artifact on disk. Spot-check `top_rules` against the same entry. **A title-count mismatch can be a TOP-RULES-ONLY sum, not a false premise — match the named per-rule counts before judging.** Some audit titles cite only the top-N rules ('N violations, top rules S607:18, S113:17, S603:15'), where N is the sum of the NAMED rules, not the repo's full `rule_counts` sum — an exact-sum check then fails (headline 53 vs a full S-select tally of 175) while every named count matches exactly. Discriminator: if the title lists specific rules with per-rule counts, verify EACH named count exactly against `rule_counts` and treat the headline as satisfied when they all match; only a full-sum title (no per-rule breakdown) takes the exact-sum rule. **Resolve the cited repo from the artifact's own `repo` values, not by transforming the row id**: the id suffix is uppercased (`PYCMP-KOBAYASHI-MARU`) while the artifact key preserves case (`Kobayashi-Maru`), so match the suffix case-insensitively — a case-sensitive grep of the id suffix returns empty and reads as a missing repo. Two count shapes beyond the single-repo sum:
   - **Whole-artifact totals** (`totals.violations`): assert `totals.violations == sum(sum(f['rule_counts'].values()) for f in findings)` once per cycle — this is the artifact's own integrity check and validates every derived count below it in the same line.
   - **Family-share rows** ("N% of the headline is rule-family X"): aggregate the family's counts across ALL findings entries, divide by the artifact total, and compare the percentage EXACTLY to the row's claim — a share computed from a stale artifact silently disagrees with a fresh one, so always derive from the freshest on-disk artifact, never the number in the row.
4. **Check the repo path.** The entry's `path` field is where the scan ran; if that path no longer exists the count may be from a moved/renamed checkout — grep the repo under the usual workdir roots before trusting or failing the count.
5. **Take the ground-truth command from the lane's usage skill, never derive it.** Each audit family's per-repo verification command is documented in the coding-hermes-audits repo at `skills/python-audit-<family>-usage/SKILL.md` (e.g. deadcode: `ruff check --select F401,F811,F841,ERA,ARG --statistics <repo>`, summed over the statistics table). Grep that file when the row title names no command — re-deriving the rule list by hand risks verifying against a DIFFERENT selection than the gatherer ran, where a mismatch proves nothing. The artifact's top-level `select` field (e.g. `"S,PT"` in the security audit JSON) names the gatherer's exact rule selection — prefer it over both the title and your guess when re-deriving. Run it from the REPO ROOT and sum in one pipe: `cd <repo> && ruff check --select <codes> --statistics . | awk '{s+=$1} END {print s}'` — the awk sum is the exact comparison number; do not eyeball a multi-line statistics table.

**Sum the statistics table by whitespace fields, never `-F'|'`.** The statistics table is tab/space-separated with the COUNT in the first column — an `awk -F'|' '{s+=$2}'` split sums to 0, and that fabricated zero reads as a verified-clean premise over a repo known to carry findings. Use the default whitespace split (`awk '{s+=$1}'`), and before trusting any computed sum eyeball the first raw output lines (`| head -3`): a zero sum over a repo with visible findings is a parse bug, not a clean repo. Read the ruff version (`ruff --version`) into the evidence note on every live re-derivation.

**The root-level invocation is part of the methodology — never probe per-subdirectory.** Ruff respects `.gitignore` by default and applies repo-level config only from the root, so a subdir-scoped probe (`ruff check sdk/python/`) changes both the ignore semantics and the effective config and can over-count several-fold; a mismatch from a subdir probe reads as drift when the premise is true. If a bare root-level run disagrees with the artifact, reconcile the gatherer's own SKIP_DIRS/config handling from its source before judging — the divergence is usually a methodology difference, not a count regression. Run the probe under `timeout` and sum with the same `awk` pipe as the root case.

**Record the scanner VERSION on both sides of a re-derivation before judging a count mismatch.** A local probe under a different `<tool> --version` than the one the row's counts came from is not apples-to-apples: rule additions, reclassifications, and different fixable-sets change counts on identical code. When versions differ, the mismatch is version-attributed until proven otherwise — put both versions in the evidence note, keep the row open with the drift noted rather than stamping premise-false or filing a count refresh, and only trust an exact match as premise-proof when the versions agree. Read the gatherer's own version line (its artifact/log) instead of assuming your local binary matches the run that produced the cited counts.

## Row-type probes (pick the cheapest per row)

- **Skip/withheld rows** (`SKIPPED-install`, `correctly withheld`): the premise is the blocker CONDITION, not the leg's output — re-test the blocker with the cheapest transport probe (`tailscale ping <host>` for an unreachable-host skip, `command -v <tool>` for a missing-tool skip) instead of re-running the leg. A blocker that now clears is an evidence refresh on the row ("retry premise holds"), not a new finding and not a close.
- **Fingerprint-only rows** (`detail` is `{fingerprint: ...}` with no evidence): the title IS the premise — verify it directly with a real command against the repo and record the command + result in the cycle log. Never file such a row as unverifiable; the fingerprint makes it checkable against the title.
- **Delivery-gap rows ("findings never landed on N owner boards") have their premise on the DESTINATION boards, not the home repo or the artifact.** Verify by checking each named destination board for a row minted by the producer family (match the family's id prefix and a run_id in `detail.evidence` newer than the gap row's `created_at`): `jq -r 'select(.id|test("PYTYP")) | [.id,.status,.created_at] | @tsv' <dest-board>`. **Read the artifact's per-finding `owning_lane` / `destination_board` fields FIRST — they prove the injection leg without touching any destination board:** set `owning_lane` values for the cited repos show the gatherer routed those findings, so only the destination rows' existence remains to check; the gap row's surviving claim is then whatever the injection does NOT prove (e.g. a fixed row cap that still drops part of the backlog) — narrow, don't close. When every named destination now carries a pending producer-family row, the gap is CLOSED — flip the row complete with the destination ids + run_ids in the close note; the destination rows' own remediation remains the foreman's work, not this row's. A partially-landed gap keeps the row open narrowed to the missing destinations.
- **Gatherer-behavior rows** (premise is what the gatherer script DOES — "silent all-clear when the tool is absent", "finding_key includes the count"): verify by reading the gatherer's source (`~/.hermes/scripts/python-*.py` — grep for the guard/mode line the row claims exists or is missing), NOT by running the gatherer. A missing guard stays provable in code after the artifact regenerates; an executed run proves only today's environment, not the failure mode.
- **Scope/exclusion rows** (premise is a repo being OUT of the scan — "repo X silently excluded"): the artifact is the cheapest evidence, because out-of-scope repos STILL appear in `findings[]` with `in_scope: false` plus a `scope_reason`. Read the repo's entry for its violations count and reason, then check the reason against the gatherer's actual scope rule (grep the remote-keyword/org-match lines in `~/.hermes/scripts/python-*.py`) — a scope claim verified by absence from the artifact proves nothing, since absence is exactly what an exclusion bug looks like.
- **Fix/close rows whose proof is an EXTERNAL artifact (S3 backup, systemd timer, remote endpoint): read the artifact back at its real location — never a repo-side proxy.** The premise is the artifact existing and being complete: list the bucket prefix (`aws s3 ls s3://<bucket>/<prefix>/` — contents present, MANIFEST/checksum listed, `latest`-style pointer read back and matching the claimed run). The repo often carries only a review copy of the changed files, and a missing unit file on the wrong host context does not refute a row whose work ran elsewhere.
- **Resolve the HOST before remote probes — do not infer it from the project or lane name.** The fleet node that shares the project's name is often just an agent/alloy satellite carrying a small config dir; the stack host is whatever the close row's `detail` names, or the node named for the service itself in `tailscale status`. Probing the wrong host yields "unit could not be found / no such directory", which reads exactly like a false premise but proves nothing; read the row's cited host first, then ssh it.
- **Wrap every remote or wide probe in `timeout N` and bound its scope** (`timeout 40 ssh <host> 'find -maxdepth N <known roots>'`): a whole-filesystem `find /` over ssh or a slow S3 endpoint can exceed the ~180s foreground window, killing the probe mid-read and burning a tick minute on a result you never see — a bounded probe that returns empty is evidence, a killed one is nothing.
- **Before failing a fix-row claim, probe the path the ROW cites — not the path you assumed.** Ship copies live under review mirrors named in the row (e.g. `stack-copy/`, workdir mirrors); absence on the main tree does not refute the fix. A verification probing a different path than the row's own citation proves nothing either way.

## Stamping the evidence refresh (row-level edit)

Append the fresh evidence entry to the row's `detail.evidence` (never rewrite the whole row), in the standard board RMW pattern: fresh re-read inside the writing script, untouched lines byte-identical, one-edit-per-targeted-id assert, re-parse every line, atomic temp+rename, then `git diff --numstat` (edits:edits, not a whole-file rewrite). DEDUPE BY `run_id`: skip the append when an entry with the same `run_id` already exists — a repeated tick otherwise stacks identical evidence lines and inflates the diff. Derive the run_id deterministically from the artifact's `generated_at` (e.g. `<family>-artifact:<first 12 hex of sha1(generated_at)>`): re-stamping the same artifact then self-dedupes, while a genuinely regenerated artifact (new `generated_at`) earns its own entry.

**Post-write sibling-merge assert: diff the board and account for every changed id, not just your targets.** On a shared family board a sibling lane can land its own evidence entries between your liveness read and your write; your RMW (built from a fresh read) preserves them, but only a diff proves the merge was clean. After the write, extract both the `-` and `+` lines of `git diff` and for every id OUTSIDE your edit set confirm the changed keys are additive `detail`/`evidence` fields only — a changed `status` or `title` on a row you did not intend to touch means your snapshot was staler than believed; re-read and re-decide before committing.

## Foreman liveness on gatherer lanes (dry_run outcome)

`outcome='dry_run'` (SCHED-GAP-1652) means a completed tick with commits=0 AND files_changed=0 — a neutral no-artifact verdict, not a failure, carrying no penalty. Before escalating a zero-artifact streak on a live lane:

1. **Scope the streak.** `SELECT project_name, COUNT(*) FROM ticks WHERE outcome='dry_run' AND spawned_at > '<window start>' GROUP BY project_name` — a streak shared by many unrelated projects is infra/operator-level context; note it, do not file a project stall.
2. **Read the foreman's session.** The `ticks.gateway_trace` JSON carries `session_id`; read the last assistant message from `~/.hermes/state.db` (`SELECT substr(content,1,900) FROM messages WHERE session_id='<id>' AND role='assistant' ORDER BY id DESC LIMIT 1`). A gatherer-style foreman may spend every tick re-running its sweep and honestly reporting REFUSED-DUPLICATES because every fresh finding already has an open row — a productive lane whose OUTPUT is reports, not commits.
3. **Check the consumption side is tracked.** If an open row already covers the queue never being drained (the real gap behind a gatherer that finds only duplicates), the cycle's output is a liveness note citing that row — not a new row and not a stall filing.

## Artifact-to-board coverage diff (the audit lane's gap sweep)

The freshest artifact doubles as the gap-hunter input for an audit-family PM lane — no delegate wave needed: list `findings[]` entries with `in_scope: true`, map each `repo` to its board row suffix, and diff against the OPEN rows' suffixes. An in-scope repo with violations and no open row is a candidate finding — but mint it only when the foreman can actually reach it: with a deep open backlog on the same repos, the right output is a watch item in the cycle report ("repo X has N violations, no open row; candidate when the current row drains"), not a new row stacked on an already-months-long queue. Never file rows for repos the scope rule excluded (`in_scope: false`) — their `scope_reason` is the gatherer's ownership verdict.

## Report shape

A verified audit row's evidence line names: artifact path, `generated_at`, and the exact sum (`rule_counts sum <repo>=N, matches row title`). That is the command-free verification the next cycle can re-derive in seconds by re-reading the artifact's timestamp.

## Alert-router rows (monitoring lanes)

Alert lanes file ONE ROW PER FIRING: the same rule re-firing later is a NEW instance the router files under its own id. This inverts the usual audit verification — the premise is the alert INSTANCE, not a produced artifact.

1. **Close against the instance, never the rule.** A row closes only on (a) its own instance's resolution — the paired `-RESOLVED` event's `endsAt` — or (b) a host-level benign verdict on THAT row's host. Never batch-close an alert family off one probe, and never close a row because the condition is quiet NOW while another instance of the same rule is still firing — the router files fresh rows for re-fires, so quiet-now only ever retires the instances you probed.
2. **Benign-OOM triage is kernel evidence, not board inference.** An OOM alert row is benign when the host kernel log shows `constraint=CONSTRAINT_MEMCG` with `oom_memcg=` inside a KNOWN test/worker cgroup (CI memcg suites, worker terminal cgroup caps). Probe with `ssh <host> 'dmesg -T | grep oom-kill'` first; fall back to `journalctl -k | grep oom` when unprivileged dmesg is empty. Pair it with a MemAvailable ratio from the alert's own Prometheus query. Put the cgroup, the victim process, and the MemAvailable number in the row's `resolution`. A recurring benign trigger (e.g. the same CI cgroup every run) is escalated in the cycle report as a watch item — the fix is an exclusion in the alert rule, NOT a re-filed row each cycle.
3. **Query the monitoring stack where it lives, and prove WHICH server you hit.** Common service ports on the PM box (9090, 9093, 3000) belong to OTHER stacks (schedulerd, <project> apps) — resolve the stack host via `tailscale status` and curl `localhost:<port>` ON that host over ssh. A 404 or a foreign-looking page is the wrong server, not a broken Prometheus: confirm identity with a cheap fingerprint (page `<title>`, `/api/v1/status/buildinfo`) before trusting any query result or declaring the stack down.
4. **Synthetic/proof rows close on absence plus provenance.** An INFO synthetic chain-proof row closes when its alertname returns zero live `ALERTS` series on the real stack AND the chain it proved is documented by an existing closure — say both in the resolution.
